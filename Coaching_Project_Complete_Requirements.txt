COACHING PROJECT — COMPLETE PROJECT REQUIREMENTS
Version: 1.0
Date: 16 September 2026

SOURCE BASIS
------------
This requirements document consolidates the requirements, architecture, implementation plan,
database design, frontend plan, validation rules, and project conventions established in the
project source/checkpoint documents uploaded for this Coaching Project.

The source material defines the application as a Student–Coach Management Application using:
- React + Vite for the frontend
- HTML/CSS/JavaScript/JSX for the frontend implementation
- FastAPI for the backend
- SQLAlchemy for database access
- PostgreSQL for persistent storage
- Alembic for database migrations
- Pydantic schemas for API validation
- Argon2-based password hashing
- JWT-based authentication

Where the source material describes an implementation recommendation rather than an explicit
assignment requirement, it is identified as a recommendation below.

======================================================================
1. PROJECT PURPOSE
======================================================================

Build a web application that connects students with coaches.

Students should be able to:
- register and log in
- maintain their profile
- discover/search coaches
- view coach details
- request coaching sessions
- view their session history/status
- cancel pending session requests

Coaches should be able to:
- register and log in
- maintain their coaching profile
- manage skills
- maintain experience information
- define availability
- set a session fee
- receive/view coaching requests
- accept or reject requests
- complete accepted sessions
- provide coach remarks
- view session history

The application must use a React frontend communicating with a FastAPI REST API.
The FastAPI backend communicates with PostgreSQL through SQLAlchemy.

4. USER ROLES
======================================================================

There are exactly two application roles:

1. STUDENT
2. COACH

Role-based access control is required.

Student-only operations must not be accessible to coaches.
Coach-only operations must not be accessible to students.

Frontend role-based routing is required for user experience.
Backend role-based authorization is required for actual security.

14. SESSION STATUS MODEL
======================================================================

Allowed statuses:

PENDING
ACCEPTED
REJECTED
CANCELLED
COMPLETED

Initial state:
- Newly created session request = PENDING

Allowed transitions:

PENDING -> ACCEPTED
PENDING -> REJECTED
PENDING -> CANCELLED
ACCEPTED -> COMPLETED

Invalid transitions include, but are not limited to:
- REJECTED -> ACCEPTED
- CANCELLED -> ACCEPTED
- COMPLETED -> CANCELLED
- COMPLETED -> REJECTED
- PENDING -> COMPLETED
- REJECTED -> COMPLETED

The backend must enforce these transitions.

The frontend should reflect the available actions but must not be relied upon for enforcement.

16. PASSWORD SECURITY
======================================================================

Password hashing:
- Argon2 through pwdlib is the established project approach
- Use a password hashing abstraction rather than implementing hashing manually

Required behavior:
- Correct password verifies successfully
- Incorrect password fails verification
- Plaintext passwords are not stored
- Password hashes are not returned through UserResponse

The project already verified the hashing foundation:
- Correct password -> True
- Wrong password -> False

======================================================================
17. AUTHORIZATION REQUIREMENTS
======================================================================

Authentication asks:
"Who is the user?"

Authorization asks:
"What is this user allowed to do?"

Student restrictions:
- A student may request sessions
- A student may view/manage their own sessions
- A student may cancel only their own pending session
- A student must not accept/reject/complete coaching requests as a coach
- A student must not modify another student's profile/session

Coach restrictions:
- A coach may view/manage their own profile
- A coach may manage their own skills/availability/fee
- A coach may view only requests assigned to them
- A coach may accept/reject/complete only sessions assigned to them
- A coach must not modify another coach's requests/profile

Backend ownership checks are mandatory for protected resources.

======================================================================
18. BUSINESS VALIDATION REQUIREMENTS
======================================================================

Registration:
- Valid email required
- Unique email required
- Valid password required
- Required user information must be supplied

Profile:
- Experience cannot be negative
- Session fee cannot be negative

Session creation:
- User must be authenticated
- User must have STUDENT role
- Coach must exist
- Session date cannot be in the past
- Duration must be positive
- Required session fields must be valid
- Requested time must respect coach availability according to the implemented availability model
- New session status must be PENDING

Session acceptance:
- Current user must be the assigned coach
- Session must be PENDING
- Requested time must not conflict with an already accepted session

Session rejection:
- Current user must be the assigned coach
- Session must be PENDING

Session cancellation:
- Current user must be the assigned student
- Session must be PENDING

Session completion:
- Current user must be the assigned coach
- Session must be ACCEPTED

======================================================================
19. SCHEDULING REQUIREMENTS
======================================================================

The system must prevent a coach from accepting conflicting sessions.

At minimum, the source requirement states that a coach cannot accept two sessions at the same date/time.

The project design recommends the stronger and more correct time-range overlap rule.

For an existing accepted session:
existing_start < requested_end
AND
existing_end > requested_start

If both conditions are true, the sessions overlap.

Example:
Existing: 10:00-11:00
Requested: 10:30-11:30
Result: CONFLICT

Scheduling checks must be performed by the backend.

The system should account for race conditions when two acceptance operations occur at nearly the same time. A transaction/database-level strategy is recommended.

======================================================================
20. TRANSACTION REQUIREMENTS
======================================================================

Operations that logically create multiple related records should be handled transactionally.

Example:
Coach registration:
- Create User
- Create CoachProfile

If one part fails:
- Roll back the transaction
- Do not leave an incomplete account

The same principle applies to other multi-step operations where data consistency is important.
